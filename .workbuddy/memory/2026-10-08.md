## 任务：诊断"识别附件都失败"问题

### 现象
用户反馈所有附件识别失败。诊断发现服务从 09:50:58 起陷入"假死→强杀→重启"无限循环（watchdog 每 40-90 秒重启一次），持续到 10:07 仍未停止。

### 根因（4 个）

1. **服务假死循环（核心）**：`service_watchdog.py` 的 `_health_ok()` 单次失败就判定假死并强杀。服务在处理长请求时（ERP 拉取 30s 超时 / OCR 多页识别）事件循环被阻塞，/api/health 无响应，watchdog 误判假死 → 强杀 → 重启 → 重启期间 health 又失败 → 恶性循环。

2. **同步阻塞**：`server.py` 的 `upload_files` / `daily_check` / `sync_punch` 都是 `async def` 但同步调用耗时操作（LLM 识别 / ERP API），阻塞 uvicorn 事件循环。

3. **`deactivate_insurance` 签名 bug**：`database.py` 签名缺 `main_policy_number` 参数，但函数体 `elif main_policy_number:` 分支引用了它，`server.py:443` 调用传了 `main_policy_number=`。导致所有减保批单入库抛 `TypeError: got an unexpected keyword argument 'main_policy_number'`。

4. **OCR 扫描件返回空**（次要，历史）：视觉模型（MiniMax-M3）对扫描件逐页返回 `[]`，识别 0 人。

### 修复（5 处代码改动）

1. `insurance_agent/infrastructure/database.py`：`deactivate_insurance` 签名加 `main_policy_number: str | None = None` 参数。
2. `service_watchdog.py`：新增 `HEALTH_FAIL_THRESHOLD = 3`，监督循环改为连续失败 3 次（约 45s）才判定假死，单次失败只计数不重启。
3. `web_app/server.py`：`upload_files` 的 `process_files()` 改 `await asyncio.to_thread(...)`（识别丢线程池，不阻塞事件循环）。
4. `web_app/server.py`：`daily_check` 的 `run_daily_check()` 改 `await asyncio.to_thread(...)`。
5. `web_app/server.py`：`sync_punch` 的 `sync_punch_data()` 改 `await asyncio.to_thread(...)`。

### 验证
- 3 个文件 py_compile 语法通过。
- `deactivate_insurance` 签名确认含 `main_policy_number`。
- LLM 底座（MiniMax-M3，ChatAnthropic）创建 + 文本调用正常（1.1s 返回）。
- `insurance_personnel` 表确认有 `UNIQUE(id_number, policy_number)` 约束，但 `upsert_insurance_personnel` 已用 `ON CONFLICT DO UPDATE` + batch 内 dedup 适配，IntegrityError 是历史遗留。

## 阳光保险《变更被保人》批单格式适配

- 批改类型：《变更被保人》
- 批文：`被保险人姓名由陈洪变更为周润,证件号码由510218198207242535变更为500381200601135218,`
- 生效日：2026-07-17

### 难点
此格式与之前所有 inline 批单不同：
- 之前所有 inline：`被保险人姓名:NAME,证件号码:ID`（marker 后跟人员信息）
- 本次：`被保险人姓名由OLD变更为NEW,证件号码由A变更为B`（**替换**语义，非简单增/减）

### 4 处核心修复

| # | 文件 | 修复点 |
|---|---|---|
| 1 | `inline_extractor.py` 新增 `_extract_change` | 解析"由X变更为Y"格式；按正则成对提取 old_name/new_name/old_id/new_id；标记 old=减保 / new=增保 |
| 2 | `inline_extractor.extract()` 路由 | 在 `_extract_replacement`（太保）后加 `_extract_change` 检测：`if "变更为" in text and "由" in text` |
| 3 | `metadata_extractor_node._INLINE_MARKERS` | 加 `"变更为"` marker，确保路由到 inline |
| 4 | `personnel_extractor_node` | 处理 `format_hint=inline` 但 `list_pages` 为空的情况（如单页批单无传统清单页），扫描所有页找到含 inline marker 的页面提取 |

### 关键技术点

**`_extract_change` 正则设计**：
```python
pattern = re.compile(
    r"姓名由\s*([\u4e00-\u9fff]{2,4})\s*变更为\s*([\u4e00-\u9fff]{2,4})"
    r"[\s\S]*?"
    r"证件号码由\s*(\d{17}[\dXx])\s*变更为\s*(\d{17}[\dXx])",
    re.MULTILINE,
)
```
- 顺序匹配：姓名 → 证件号码
- `[\s\S]*?` 非贪婪匹配中间所有内容（可能是换行/逗号等）
- 一次 `finditer` 可处理多组变更

**personnel_extractor_node 修复**：
```python
if not list_pages and format_hint == "inline":
    pages_to_extract = [
        p.page_number for p in pdf_doc.pages
        if any(m in p.text for m in _INLINE_MARKERS)
    ]
    if not pages_to_extract:
        pages_to_extract = [p.page_number for p in pdf_doc.pages]
else:
    pages_to_extract = list_pages
```
- 之前逻辑：`for page_num in list_pages`，list_pages 空则 0 提取
- 之后：先扫所有页找含 inline marker 的页面；都找不到再兜底扫所有页

### 服务进程陷阱（重要教训）

**问题**：`/api/agent/reload` 反复调用无效，DEBUG print 始终不出现，但本地 Python 直接 import 模块运行新代码却 OK。

**根因**：服务进程（PID 14180）在某种 shell 权限隔离下无法被 `Stop-Process -Id 14180 -Force` 或 `taskkill /F /T` 终止（返回 exit code 1 但进程仍在）。`/api/agent/reload` 重建 graph 但 Python 模块缓存或某些 hook 让新代码未生效。

**解决方案**：Win32 API 直接终止
```python
import ctypes
handle = ctypes.windll.kernel32.OpenProcess(1, False, pid)
ctypes.windll.kernel32.TerminateProcess(handle, 1)
```
**唯一可靠方式**。教训：遇到代码改动 reload 不生效时，不要反复调 `/api/agent/reload`，直接 Win32 API 强杀进程让 watchdog 重启。
