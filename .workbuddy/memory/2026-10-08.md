## 任务：诊断"识别附件都失败"问题

### 现象
用户反馈所有附件识别失败。诊断发现服务从 09:50:58 起陷入"假死→强杀→重启"无限循环（watchdog 每 40-90 秒重启一次），持续到 10:07 仍未停止。

### 根因（4 个）

1. **服务假死循环（核心）**：`service_watchdog.py` 的 `_health_ok()` 单次失败就判定假死并强杀。服务在处理长请求时（ERP 拉取 30s 超时 / OCR 多页识别）事件循环被阻塞，/api/health 无响应，watchdog 误判假死 → 强杀 → 重启 → 重启期间 health 又失败 → 恶性循环。

2. **同步阻塞**：`server.py` 的 `upload_files` / `daily_check` / `sync_punch` 都是 `async def` 但同步调用耗时操作（LLM 识别 / ERP API），阻塞 uvicorn 事件循环。

3. **`deactivate_insurance` 签名 bug**：`database.py` 签名缺 `main_policy_number` 参数，但函数体 `elif main_policy_number:` 分支引用了它，`server.py:443` 调用传了 `main_policy_number=`。导致所有减保批单入库抛 `TypeError: got an unexpected keyword argument 'main_policy_number'`。

4. **OCR 扫描件返回空**（次要，历史）：视觉模型（MiniMax-M3）对扫描件逐页返回 `[]`，识别 0 人。

### 修复（5 处代码改动）

1. `insurance_agent/infrastructure/database.py`：`deactivate_insurance` 签名加 `main_policy_number: str | None = None` 参数。
2. `service_watchdog.py`：新增 `HEALTH_FAIL_THRESHOLD = 3`，监督循环改为连续失败 3 次（约 45s）才判定假死，单次失败只计数不重启。
3. `web_app/server.py`：`upload_files` 的 `process_files()` 改 `await asyncio.to_thread(...)`（识别丢线程池，不阻塞事件循环）。
4. `web_app/server.py`：`daily_check` 的 `run_daily_check()` 改 `await asyncio.to_thread(...)`。
5. `web_app/server.py`：`sync_punch` 的 `sync_punch_data()` 改 `await asyncio.to_thread(...)`。

### 关键技术点

**`_extract_change` 正则设计**：
```python
pattern = re.compile(
    r"姓名由\s*([\u4e00-\u9fff]{2,4})\s*变更为\s*([\u4e00-\u9fff]{2,4})"
    r"[\s\S]*?"
    r"证件号码由\s*(\d{17}[\dXx])\s*变更为\s*(\d{17}[\dXx])",
    re.MULTILINE,
)
```
- 顺序匹配：姓名 → 证件号码
- `[\s\S]*?` 非贪婪匹配中间所有内容（可能是换行/逗号等）
- 一次 `finditer` 可处理多组变更

**personnel_extractor_node 修复**：

### 服务进程陷阱（重要教训）

**问题**：`/api/agent/reload` 反复调用无效，DEBUG print 始终不出现，但本地 Python 直接 import 模块运行新代码却 OK。

**根因**：服务进程（PID 14180）在某种 shell 权限隔离下无法被 `Stop-Process -Id 14180 -Force` 或 `taskkill /F /T` 终止（返回 exit code 1 但进程仍在）。`/api/agent/reload` 重建 graph 但 Python 模块缓存或某些 hook 让新代码未生效。

**解决方案**：Win32 API 直接终止
```python
import ctypes
handle = ctypes.windll.kernel32.OpenProcess(1, False, pid)
ctypes.windll.kernel32.TerminateProcess(handle, 1)
```
**唯一可靠方式**。教训：遇到代码改动 reload 不生效时，不要反复调 `/api/agent/reload`，直接 Win32 API 强杀进程让 watchdog 重启。

### 3 个核心问题

**问题 1：身份证脱敏新格式 14+4 不识别**
PDF 中身份证：`51102519741110****`（6 地区码 + 4 年 + 2 月 + 2 日 + 4 星，共 18 字符）。
旧正则只支持：
- 完整 18 位：`\d{17}[\dXx]`
- 6+8+4 脱敏（PEAC）：`\d{6}\*{6,10}\d{2,4}[\dXx]?`

→ 14+4 格式两种正则都不匹配 → 0 人提取。

**问题 2：table_extractor job_title 提取逻辑吃掉了岗位名称**
表头：`序号 / 姓名 / 证件号码 / 职业类别 / 岗位名称`
- 职业类别列存"三类职业"
- 岗位名称列存"绿化栽植工"

旧逻辑：
```python
occ_match = self._OCCUPATION_CLASS_PATTERN.search(post_region)
if occ_match:
    job_title = occ_match.group(1).replace(" ", "")  # ✗ 立即赋值给 job_title
# 下面的 _JOB_PATTERN.finditer 看到 job_title 已有值就 break → "绿化栽植工"被跳过
```

→ job_title="三类"，occupation_class=""。

**问题 3：跨行工种合并规则（4b）误合并 X类职业 + 工种**
表格行格式：`51102519741110****\n三类职业\n绿化栽植工`

4b 规则（合并跨行工种）：
```python
r'((?!是|否|有|无)[\u4e00-\u9fff（])\n((?!雇员|员工|人员)[\u4e00-\u9fff]{1,8}(?:工|员|师|者|人))'
```
- 前段"业"（"职业"的"业"）+ \n + 后段"绿化栽植工" → 匹配

**修复 5：`table_extractor` 跨行工种合并规则（4b）占位符保护**

为防止 4b 把"X类职业\n绿化栽植工"误合并，在 4b 之前先把"X类职业"占位符化：
```python
_PLACEHOLDER = '\ue000'  # U+E000 私有区字符，PDF 文本里绝不可能存在
list_text = re.sub(
    r'([一二三四五六七八九十])\s*类\s*职\s*业',
    lambda m: m.group(1) + '类职业' + _PLACEHOLDER,  # 占位符放"职业"后
    list_text,
)
list_text = re.sub(...)  # 4b 合并跨行工种（占位符保护住"职业"和"绿化栽植工"不合并）
list_text = list_text.replace(_PLACEHOLDER, '')  # 还原
```

**占位符位置关键**：必须放在"职业"之后，不能放在"职业"中间。否则 4b 仍会匹配"业"+"\n"+"绿化栽植工" → 合并。

不能用 `\x00` 因为 `re.sub` replacement string 把 `\x00` 当 regex 转义解析报错。
改用 `\ue000`（U+E000 私有区字符），但要通过 lambda 注入（replacement string 也支持 `\uxxxx` 但同样会被解析）。

### 教训
1. **脱敏 ID 格式不止一种**：PEAC 6+8+4、平安产险 14+4，未来可能还有更多（如完全星号）。通用正则 `(?:\d{6}\*{6,10}\d{0,4}[\dXx]?|\d{14}\*{4})` 是务实方案。
2. **"职业类别"和"岗位名称"是两个不同字段**：前者是分类等级（一类~六类），后者是具体工种。PEAC 只有职业类别，平安产险有两者。提取时必须分字段存储，不能合并。
3. **跨行合并规则的边界 case**：4b 合并跨行工种本意是处理"起重装卸机械\n操作工"，但贪婪匹配会把"X类职业\n绿化栽植工"误合并。占位符保护是稳妥做法。
4. **占位符必须放在不被 4b 匹配的位置**："类职业" 中间放占位符（"类\ue000职业"）会被前段"业"+\n+后段匹配；放"职业"后（"类职业\ue000"）前段是占位符（不在 [\u4e00-\u9fff]）→ 不合并。
