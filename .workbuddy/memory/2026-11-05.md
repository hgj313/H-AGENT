**判定规则**（`_decide_replace`）：
1. 新数据排序键更大（止期更晚→起期更晚）→ 替换
2. 新数据更小 → 跳过；**例外**：旧记录止期未知（空）且新数据仍在有效期内 → 用更具体的数据替换
3. 完全等价 → 仅当新数据能补齐旧记录某个空字段时才替换
4. 排序键**不含 id**（见下方教训）

**日期保护**：新数据日期为空时保留原记录日期（不覆盖）→ 避免在保人员被误降为失效（11-03 踩过）。

**收敛历史重复**：库中若已有该人多条记录，替换时先吸收其余行的非空字段，再删除其余行 → 一人一行。

## 本次沉淀的经验（易踩坑）

1. **排序键里的 id 项不能参与「新 vs 旧」比较**。`_personnel_rank` 含 id（用于在多条历史行之间
   选目标），若直接拿去比较"新数据 vs 库中记录"，库中已有行会因 id 更大而永远赢过新数据，
   导致新数据永远无法替换。必须只取前 4 项。
2. **对比两个排序键时，元组元素语义必须同构**。我曾用 `(sd,ed,eff,hp,id)` vs `(ed,sd,eff,id)`
   比较（元素错位 → 逐位比的是 sd vs ed），得出"186 组不一致"的错误结论；改成同构后是 **0 组**。
   同理 `_personnel_rank` 的 end/start 顺序与离线工具不同是有意为之（end 优先更安全：
   避免选中"起期更晚但止期更早"的短区间把在保人员降级），且在 218 组实测上与工具结果 0 分歧。
3. **`database.py` 模块末尾有一句模块级 `init_db()`** → 任何 `import` 都会对**默认 DB_PATH**
   执行建表/建索引。我写验证脚本时 `import` 后才改 `dbmod.DB_PATH`，导致唯一索引建到了**线上库**
   （数据零变更，服务重启时本来也会做同样的事，但以后要注意 import 顺序）。
4. **日志在 `server.err.log` 不是 `server.log`**：`logging.StreamHandler()` 不带参数时写 **stderr**，
   server.py 里的注释写"stdout"是不准确的。`server.log` 只有 uvicorn 的 access log。
   另：server.log / server.err.log 是 GBK 编码，grep 中文会乱码。
5. **`netstat` / `tasklist` 输出是 GBK** → subprocess 读要用 `encoding="mbcs", errors="replace"`，
   否则 UnicodeDecodeError。`wmic` 在 Win11 24H2 已弃用，改用 `tasklist`。
6. **唯一索引与表级 UNIQUE 的相互作用**：建了 `UNIQUE(name,id_number)` 后，
   "保单号不同就新增行"这条老路彻底堵死；写侧必须先按 (name,id_number) 查库再决定新增/替换。
