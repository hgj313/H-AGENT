## 排查：打卡「无正常保险人员」同步飞书多维表格时缺少「项目」等信息

### 用户诉求
「检查下为什么保险管理AI助手里面的打卡无正常保险人员数据同步到飞书多维表格时。缺少了项目等信息」

### 结论：本地与传输层全部正常，根因在**飞书自动化流程的「输出设置」JSON Schema**

**三层判定法**（本次沉淀的关键方法论）

| 层 | 检查方式 | 本次结果 |
|---|---|---|
| ① 本地数据层 | `punch_records` 表字段空值统计 | ✅ `project_name` 空值 **0/223**（`category_name` 空 32%，是 ERP 侧真实缺值） |
| ② 推送载荷层 | 实发 payload + 响应码 | ✅ 11 字段全带，`code=0` |
| ③ 飞书映射层 | — | ❌ **schema 未声明 → 表格列必然空** |

### 关键实验（决定性证据）

1. **递减字段集探测**（P1 仅 name → P5 加 project_name）：全部返回 `{"code":0}`
2. **塞入完全不存在的字段** `完全不存在的字段_zzz`：**仍返回 `code=0`**
   → 证明飞书 webhook **触发器不校验字段**，接收即成功
   → 反推：**字段→列的映射完全由自动化流程的「输出设置」决定**
3. **查飞书官方文档**确认机制：
   - 「输出设置」→「通过发送请求设置」：飞书监听最近 3 分钟内发到该 webhook 的请求，
     取**最新一条**，生成**不可修改**的请求体示例结构（JSON Schema）
   - 下游「添加记录」节点**只能引用 schema 中已声明的字段**
   - 「如果你引用了 webhook 信息后，又修改了输出设置中的输出示例，引用会失效」
   - ⚠️ 所以 schema 是**一次性快照**：早期用 4 字段 payload 生成的 schema，
     后续即使推 11 个字段，schema 外字段也无法被引用 → 表格列永远空
4. **历史佐证**：`.workbuddy/memory/2026-09-30.md:151`
   「用户截图飞书自动化流程"通过发送请求设置"页面**只看到 4 个字段**」→ schema 只有 4 个字段

### 教训

1. **「webhook 返回 code=0」不等于「字段落库了」** —— 触发器只管接收，
   落库靠自动化流程的 schema + 逐列映射，**这是两个完全独立的环节**
2. **飞书自动化 webhook 的 schema 是一次性快照且不可修改** → payload 字段集变更后
   必须重新生成 schema + 重新绑定引用，否则新字段静默丢失（不报错！）
3. **排查「某列为空」必须分层**（本地 → 载荷 → 映射），
   否则会把飞书端的配置问题误判成数据源问题
4. **日志要打印实际发送的全字段**，只打 `name`+`punch_time` 会让排查彻底失明
   （本次就是靠补全字段摘要才把问题锁定在第三层）
5. `punch_records` 每天 00:00 清空昨日数据（`days_to_keep=1`）→
   **历史打卡无法回溯**，跨天排查必须当天做或查日志
