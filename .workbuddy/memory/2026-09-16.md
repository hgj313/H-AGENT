### 根因链（三处缺陷叠加）
1. **写入层无校验**（根因）
   - `database.py upsert_insurance_personnel` L625：`status = p.get("status", "正常")`
   - `database.py add_insurance_personnel` L697：同上
   - `database.py update_personnel`：直接透传 `_EDITABLE_FIELDS` 里的 status
   - `web_app/server.py _parse_personnel_excel` L1803：`status = _get("状态")` 直接读 Excel 列
   - **四处全部无条件信任输入**，没有白名单
2. **检测层严格等值**
   - `database.py get_active_insurance_by_id`：`WHERE status = '正常' AND ...`
   - '增保' ≠ '正常' → 漏匹配 → 进 uninsured_list → 误判未参保
3. **后果被放大**：`daily_check_service` / 实时覆盖检查拿到 uninsured 后直接发邮件+短信给项目经理

### 修复（三层防御）

**第 1 层：写入层白名单归一化** (`database.py`)
- 新增 `normalize_person_status(raw, end_date, today)`（内部别名 `_normalize_status`）
- 映射表 `_MODIFICATION_TO_STATUS`：增保/批增/增加/新增→正常；减保/批减/减少/删除→失效
- 优先级：①白名单原样返回 ②批改类型映射 ③未知值按 end_date 推断
- **关键改进**：批改类型映射后**再用 end_date 校正**——'增保'+已过期 → '失效'（首版漏了这步，测试发现后修正）
- 接入点：`upsert_insurance_personnel` / `add_insurance_personnel` / `update_personnel`

**第 2 层：Excel 导入** (`server.py _parse_personnel_excel`)
- `status = db.normalize_person_status(raw_status, end_date, today)`

**第 3 层：检测层兜底** (`get_active_insurance_by_id`)
- `status = '正常'` 严格等值 → 改为排除式 `(status IS NULL OR status = '' OR status != '失效')`
- 即使未来再出现未知 status，也**不会**把期内人员误判为漏保（宁可漏报不可误报）
