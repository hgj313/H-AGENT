## 打卡数据同步飞书多维表格 —— 方案调研（未实施）

### 现状盘点
- **打卡获取逻辑（现成可复用）**：`ERPClient.fetch_all_punch_data(punch_date, page_size=500)`
  （`insurance_agent/infrastructure/erp_client.py:139`，HMAC-SHA256 签名 + 分页）
  → `coverage_check.sync_punch_data()`（三接口并发：punch/projects/users）
  → `db.upsert_punch_records()` → 表 `punch_records`
  （UNIQUE(punch_date, identification_number)）
- **实时链路**：MQ → `realtime_punch_consumer.py:377` 也调 `db.upsert_punch_records(norm, punch_date)`
  → 覆盖检查 → `push_uninsured_person()`（仅未参保人员）
- **数据量**：2026-11-10 单日 449 条打卡记录（库里目前仅此 1 天）

### 关键结论
现有飞书通道 `insurance_agent/tools/feishu_webhook_pusher.py` 用的是**飞书「自动化流程」webhook**
（`.feishu_webhook.json`，webhook_url = `https://gsegreen.feishu.cn/base/automation/webhook/event/...`），
特点：一次一条 POST、只能新增不能改、限 10 QPS → **不适合全量每日打卡同步**，需新建 Bitable 开放 API 通道。

`feishu-uploader-plugin/` 是飞书多维表格**自动化插件**（附件 PDF → 本地 `/api/upload`），方向相反，与本需求无关。

### 推荐方案（分层，遵循 AGENTS.md 的 DI/DDD 要求）
- 新增 `insurance_agent/infrastructure/feishu_bitable_client.py`（基础设施层，只管鉴权与 HTTP）
  - `POST /open-apis/auth/v3/tenant_access_token/internal` 取 token（缓存 ~2h）
  - `batch_create`（≤500 条/次）/ `batch_update` / `list_records` / `list_fields`
- 新增 `insurance_agent/tools/punch_bitable_sync.py`（工具层，业务编排）
  - 唯一数据源 = 本地 `punch_records` 表，**不重复拉 ERP**
  - 幂等：业务主键「证件号+打卡日期」，飞书侧记录 `record_id` 映射到本地新表 → 重复同步只 update
  - 分批 500、失败重试、DLQ 落盘
- 配置独立 `.feishu_bitable.json`（app_id/app_secret/app_token/table_id/字段映射），与既有 `.feishu_webhook.json` 解耦
- 挂载点：scheduler 新增 `feishu_sync` 任务（time_key 如 `feishu_sync_time`）+ `POST /api/punch/sync-to-bitable` 手动触发

### 飞书 API 注意事项
- 日期列必须传 **13 位毫秒时间戳**（int），不能传字符串
- 数字字段传 int/float，不接受布尔；单选字段传**已存在的选项名**字符串，不存在报 1254062
- `app_token` 从 Base URL `/base/` 后取；`table_id` 用 `GET /apps/{app_token}/tables` 列出
- 权限：`bitable:app`（查看、评论、编辑和管理多维表格），自建应用需发布版本后生效
