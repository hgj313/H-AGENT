## 一、混合增/减保批单行级误判 —— 根因定位与修复

### 现象（用户报告）
> 「该保单中一共两个人，一个是删除（减保）一个是新增（增保）。但助手提取出来两个都是减保。」

（黄河财产保险批单 `662290212192026BZN00000765-008`，保险期 2026-11-13 ~ 2026-12-13）

《雇员变动清单》2 人：
| 姓名 | 证件号 | 状态列 | 正确判定 |
|---|---|---|---|
| 杨廷林 | 532625198302112510 | 删除 | 减保 |
| 李运容 | 452428196804142022 | 新增 | **增保**（误判成减保） |

### 端到端复现（基线，修复前服务）
`POST /api/upload` → `total_persons=2, total_add=0, total_remove=2`（两人均判减保）✅ 复现

### 根因
黄河《雇员变动清单》表头 = `序号|姓名|证件号|职业代码|职业/工种|状态|备注`，
**状态列在证件号列右侧**（PDF 坐标 x=420 > x=197）。

`table_extractor` 的行级判定：
- `pre_region` = 回溯到「上一个身份证号之后」→ 李运容行的 pre_region =
  `'\n31010\n20014\n农夫\n删除\n2\n李运容\n'` ← **吞进了上一行的「删除」状态单元格**
- `post_region` = 截断到「下一个身份证号之前」→ `'452428196804142022\n31010\n20014\n农夫\n新增\n...'`
- 原实现 `_detect_row_modification_type(pre + post)` 是**「减保优先」的全局扫描**
  → 「删除」抢先命中 → 李运容被判减保

### 修复（`insurance_agent/extractors/table_extractor.py`）
新增 4 个类方法 + 2 个正则常量：
- `_STATUS_COLUMN_PATTERN` = `变动类型|变更类型|批改类型|增删类型|变动情况|变更情况|人员变动|状态`
- `_ID_COLUMN_PATTERN` = `证件号码|身份证号码|身份证件号码|证件号|身份证号`（长名优先）
- `_detect_status_column_side(list_text, first_id_pos)` → `"after"/"before"/""`
  原理：PDF 表格表头在抽取文本中按**从左到右**出现，比较两列名的文本位置先后即可还原左右关系
- `_first_marker_in(region, prefer_standalone)` → **位置优先**（与原「减保优先」的全局扫描相反）
- `_is_standalone_cell(region, start, length)` → 标记是否为独立单元格（前后是换行/边界）
- `_detect_row_modification_type_by_column(pre, post, list_text, first_id_pos)` → 消歧入口

规则：
- 状态列在证件号列**右**侧 → 取 `post_region`（黄河《雇员变动清单》）
- 状态列在证件号列**左**侧 → 取 `pre_region`（中国人寿《被保险人变动清单》）

### ⚠️ 零影响设计

2. 新逻辑**仅在「同时命中增标记和减标记」的歧义场景**启用；单标记场景完全走原逻辑
3. 调用点改为 `self._detect_row_modification_type_by_column(pre_region, post_region, list_text, first_id_pos)`

## 二、飞书端部署消费者程序 —— 概念澄清（承接 11-10）

**结论：消费者程序不在飞书端跑。**
飞书开放平台是「被调用方」——不提供常驻进程运行环境，也无法主动订阅外部 MQ。
飞书端只需完成**授权 + 建目的地**；消费者程序仍跑在能同时访问
「阿里云 RocketMQ 公网 HTTP 接入点」与「飞书开放平台」的机器上（即用户本机 Windows）。

产出：`erp_feishu_direct/probe.py`（独立自检脚本，不依赖 8765）
+ `tests/test_erp_feishu_direct_probe.py`（7 项）
+ `DOCS/ERP直连飞书多维表格指南.md` 新增「谁跑在哪」对照表与「自检」章节

### 实测纠正的 3 个 MQ 认知错误
1. 桥接消费组真实名是 **`insurance-automation`**（`mq_bridge_stderr.log` 实测），
   历史文档里的 `GID_INSURANCE_AGENT_PROCESS` **并不存在**（实测 403 not created）
2. **`/consumer/groupStatus` 不能用来判消费组是否存在** —— 管理级接口，用消费 AK 调用固定 403
   `OwnerId ... forbidden`，连已存在的组也查不出（假信号）。
   正解：消费端点探活 → `404 MessageNotExist`=组存在 / `403 not created`=组不存在
3. **消费的 tag 也参与资源键校验** → 拿不存在的 tag 去消费，即使组存在也报 not created

直连链路消费组定为 **`feishu-direct-sync`**（与实例现有命名风格一致，无 `GID_` 前缀）。
